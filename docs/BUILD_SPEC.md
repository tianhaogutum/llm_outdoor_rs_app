# Build spec: from rule-based scorer to an evaluated multi-stage recommender

Working document for the coding agent and the repo owner. Execute one phase at a time. Each phase ends with acceptance checks; do not start the next phase until they pass and the owner has reviewed the diff.

> Decisions taken while executing this spec (data source, providers, deviations) are recorded in [DECISIONS.md](DECISIONS.md).

## 0. Ground rules

- **Branch:** all work on `recsys-upgrade`. Never push to `main`. Small commits, one logical change each, honest dates (no backdating, no history rewrites).
- **No invented numbers.** Every metric that appears in the README or docs must be generated by `make eval` and read from `eval/results/*.json`. If a result is disappointing, report it as is.
- **Synthetic is labelled synthetic.** Simulated users and LLM-judged labels are named as such wherever results are shown.
- **Keep the baseline.** The current content-based scorer in `backend/app/services/recommendation_service.py` stays available as system `v0_rules`. New stages are added beside it and switched by config.
- **No secrets in the repo.** Vertex AI is reached through Application Default Credentials that the owner sets up. The agent never asks for, prints, or stores keys or tokens.
- **Stop at decision points.** Items marked OWNER DECISION or OWNER CHECKPOINT need the owner; stop and ask instead of guessing.
- **Cost control.** All LLM, embedding and ranking calls go through one client module with an on-disk cache (keyed by model + input hash) and a per-run budget counter that aborts when exceeded. Tests and CI use a mock provider and make no network calls.

## 1. Where the repo is today

- FastAPI + async SQLite + Alembic backend, Next.js frontend, ~12k lines.
- Catalogue: 111 Outdooractive routes in a committed `backend/data/app.db`; 1 profile, 0 feedback rows. The raw tours JSON the import scripts expect (`backend/data/outdooractive/…`) is not in the repo.
- Recommender: weighted sum of difficulty (0.4), distance (0.3) and tag Jaccard (0.3), hand-tuned; per-route score breakdown returned to the UI.
- Feedback: four negative reasons shift the user vector and down-weight the route (0.5 / 0.1 / 0.01, filtered at 4).
- LLM (local Ollama, `llama3.1:8b`) is used only for narrative text and SVG souvenirs, not for recommendation.
- Entry point for preferences is a 3-question questionnaire; no chat.
- No tests, no CI, no evaluation, not deployed.

Known defects to fix in Phase 0:

- `calculate_time_decay_weight` is never given a real age: `days_ago` is hard-coded to `0.0` because `ProfileFeedback` has no timestamp.
- The same function is documented as a half-life but computes `exp(-t / half_life)` (0.37 at one half-life instead of 0.5).
- Difficulty scale is inconsistent: a docstring says 0–6, the feedback adjustment clamps at 3. Check the data and make one scale explicit.
- README references `backend/scripts/test_models.py`, which does not exist.
- `frontend/tsconfig.tsbuildinfo` is tracked.

## 2. Target architecture

```
questionnaire + chat ──► preference model (structured slots + free-text intent)
                                   │
                         hard-constraint filter        (deterministic)
                                   │
                 candidate generation: BM25 + dense, RRF fusion   (recall)
                                   │
                 ranking: learned ranker over stage features      (precision)
                                   │
                 re-ranking: diversity (MMR), feedback, exploration
                                   │
                 explanation: per-stage score breakdown + grounded text
```

Design principle to keep visible in code and docs: **similarity proposes, verifiable constraints decide eligibility, and every stage reports its contribution so a result can be explained and audited.**

## 4. Phases

### Phase 0 — Hygiene and a trustworthy baseline (½ day)

- Create branch. Untrack `tsconfig.tsbuildinfo`. Fix the README.
- Export routes to `backend/data/seed/routes.jsonl`; add `make seed` that rebuilds the DB from it; stop tracking `app.db`.
- Alembic migration: `created_at` on `profile_feedback`; wire real age into the decay; fix the half-life formula; settle the difficulty scale.
- `backend/tests/`: unit tests for every scoring function, the feedback adjustment (including edge clamps) and the decay. Add ruff and a GitHub Actions workflow (lint + tests, `LLM_PROVIDER=mock`).
- Introduce the single LLM/embedding/rank client with cache, budget, providers. Port the existing narrative calls to it; Ollama path keeps working.

**Acceptance:** `make test` green locally and in CI; app still runs end to end with `LLM_PROVIDER=ollama` and with `vertex`; no behaviour change in `v0_rules` except the two decay fixes (covered by tests).

### Phase 1 — Data (1 day)

OWNER DECISION: source for a larger catalogue.

- Option A: Outdooractive API, if the owner still has a valid key and the terms allow this use. Also check whether the terms allow the route texts to sit in a public repo; if not, keep content out of git and ship only IDs plus a fetch script.
- Option B: open data (e.g. OpenStreetMap hiking relations, ODbL attribution) enriched with elevation, if A is not available.

Target: at least 3,000 routes in one coherent region, each with title, text description, tags, category, difficulty, length, ascent, duration, start coordinates. Write `docs/DATA.md`: source, licence, counts, distributions, missing-value rates, dedup rules.

**Acceptance:** `make data` reproduces the catalogue; `make data-stats` prints the figures used in `docs/DATA.md`.

### Phase 2 — Evaluation harness before any new model (1 day)

There is no real traffic, so evaluation is built on simulated users and judged relevance, with the limits stated openly.

- **Personas** (`eval/personas/`): ~300 simulated users. Each has structured latent preferences (fitness, distance band, home location, tag affinities) and a free-text intent (e.g. "quiet lake loop with a hut stop, fine for a seven-year-old"). Fixed seed. Split dev / test by persona.
- **Judgements:** pool the top-k from every system per persona (TREC-style pooling), grade each (persona, route) pair 0–3 with an LLM judge and a written rubric. Store judgements in `eval/qrels/`.
- **OWNER CHECKPOINT:** the owner hand-labels 150 pairs blind. Report agreement between owner and judge (weighted kappa). If agreement is poor, fix the rubric before trusting any number.
- **Metrics:** NDCG@10, MRR, Recall@50 for candidate generation, hard-constraint violation rate, catalogue coverage@10, intra-list diversity, p50/p95 latency, cost per request. Bootstrap 95% confidence intervals.
- **Systems registry:** `random`, `v0_rules`, then each later variant, selected by name. `make eval SYSTEM=…` writes `eval/results/<system>.json`; `make report` renders `docs/RESULTS.md` from those files only.
- **Guard against circularity:** persona utility must not be the same functional form as `v0_rules`. Part of relevance must depend on the free-text intent and on attributes the rule scorer does not see. State this in `docs/EVAL.md`.

**Acceptance:** `random` and `v0_rules` rows in `docs/RESULTS.md` with CIs; rerun is deterministic from cache; `docs/EVAL.md` explains protocol and limitations.

### Phase 3 — Multi-stage retrieval and ranking (2 days)

Add one component per commit and rerun the evaluation each time.

- **3a. Hard filters:** category, radius from home, absolute distance cap. Report violation rate before/after.
- **3b. Candidate generation:** BM25 over title + description + tags; dense retrieval with the embedding model; reciprocal-rank fusion. At a few thousand items use exact cosine over a numpy matrix and say so in the docs, including at what scale an ANN index would become necessary.
- **3c. Ranking, two variants compared:** (i) Vertex semantic ranker on the top 50; (ii) a learned ranker (LambdaMART via LightGBM) over stage features: the three rule sub-scores, BM25 score, dense similarity, ranker score, distance from home, ascent fit. Train on dev personas only. Report feature importance.
- **3d. Diversity:** MMR over the final list; sweep lambda and show the NDCG-vs-diversity trade-off.
- **Explanations:** extend the existing score breakdown so the API returns each stage's contribution; update the score modal in the UI to show it.

**Acceptance:** ablation table in `docs/RESULTS.md` (`v0_rules → +filters → +bm25 → +dense → +rrf → +ranker → +mmr`) on the test split; every stage toggled by config; p95 latency within an agreed budget; unit tests for fusion, MMR and feature building.

### Phase 4 — Conversational preference elicitation (1 day)

- `POST /api/v1/profiles/{id}/chat`: the LLM returns structured output validated by a Pydantic schema: slot updates (difficulty band, distance band, tags to add/remove, region) plus a free-text intent string. Slots feed the filters and rule features; the intent string feeds retrieval. If a required slot is missing, ask one clarifying question (max two turns).
- Treat catalogue text and user text as data, never as instructions.
- Frontend: chat box in onboarding and a "refine" box on the results page.
- Evaluation: ~60 scripted utterances with expected slots → slot precision / recall; end-to-end NDCG@10 for questionnaire-only vs questionnaire + chat.

**Acceptance:** slot metrics and the end-to-end comparison in `docs/RESULTS.md`; schema-violation rate reported; tests run against the mock provider.

### Phase 5 — Feedback loop and implicit signals (1 day)

- Route completions (souvenir records) become positive implicit feedback; existing negative reasons stay. Apply the fixed time decay to both.
- User representation update: intent embedding moved toward completed routes and away from rejected ones (Rocchio-style), alongside the existing slot adjustments.
- Cold start: reserve one slot in the top 10 for exploration (Thompson sampling over tag clusters); measure its cost in NDCG and its gain in coverage.
- Simulation: 10 feedback rounds per test persona; plot NDCG@10 by round for `v0_rules` and the new system; save the figure under `docs/`.

**Acceptance:** convergence plot and table generated by `make simulate`; unit tests for updates and exploration.

### Phase 6 — Ship and write it up (1 day)

- Dockerfile; backend serves the static frontend as today. Pre-generate narrative content so the demo does not depend on a live LLM for stories. Rate limit and budget cap on the public demo.
- OWNER CHECKPOINT: deployment target, public URL and spend need the owner's approval before anything is deployed.
- README rewritten as a short technical report: what it does, architecture diagram, results table, convergence plot, failure analysis (the ten worst-ranked test queries and why), limitations (simulated users, judge bias, catalogue size), and what would change with real traffic (online experiments, interleaving, counterfactual evaluation).
- A "Project history" section stating what the original course project contained and what was added in this extension, with dates.

**Acceptance:** fresh clone → `make seed && make test && make eval` works from the README alone; demo URL loads and returns explained recommendations.

## 5. Owner review list

After each phase the owner should be able to answer, without notes:

1. Why pooling for judgements, and what bias does it introduce?
2. What does agreement between my labels and the LLM judge tell me, and what would I do if it were low?
3. Why RRF rather than a weighted score sum for fusing BM25 and dense results?
4. Which stage contributed the most NDCG, and which contributed nothing?
5. Where does the learned ranker overfit to the simulated users?
6. What is the cost and p95 latency per request, and which stage dominates?
7. Which failure cases remain, and what data would fix them?
8. What would I measure first if this had real users?

If any answer is unclear, rerun that experiment by hand before moving on.
