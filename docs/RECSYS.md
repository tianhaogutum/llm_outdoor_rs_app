# The recommender pipeline (Phase 3)

Design of the multi-stage recommender in `backend/app/recsys/`, what each stage does and why, the
explanation schema, and where its measurements live. **No result is typed here**: every number is in
[RESULTS.md](RESULTS.md) (generated by `make report` from `eval/results/*.json`), and this document
points to the section. Parameters (k, depths, lambda) are configuration, not results. Decisions and
deviations: [DECISIONS.md](DECISIONS.md) D11-D16, D19-D23 (Phase 4/5). Protocol: [EVAL.md](EVAL.md).

Read every result with EVAL.md's caveat: simulated users, LLM-judged relevance, judge not yet validated
against the owner's labels.

## 1. Shape

```
UserQuery (user vector, tab, home, radius, distance cap, intent)
   │
filter          category tab · radius from home · distance cap            (filters.py)
   │
needs           (iteration 2, if configured) stated, verifiable needs narrow the set; relaxed below a floor  (needs.py)
   │  eligible set (tens to ~1,000 routes)
   ├── BM25F over title / description / tags   ─┐                          (bm25.py, text.py)
   ├── dense: intent embedding · exact cosine  ─┤ top 100 each              (dense.py)
   │                                            ▼
fusion          reciprocal-rank fusion, k = 30, keep top 50                 (fusion.py)
   │
ranker          none | v0 rules | ranker API | learned (LambdaMART)         (pipeline.py, features.py, ltr.py)
   │
feedback        (Phase 5, if configured) drop recent completions/rejections, re-score  (feedback.py)
   │
mmr             lambda = 0.8 on embedding similarity                       (mmr.py)
   │
explore         (Phase 5, if configured) one reserved slot, Thompson over tag clusters  (explore.py)
   │
Recommendation  route ids + scores + per-stage StageTrace with per-route contributions  (result.py, explain.py)
```

Principle: similarity proposes, verifiable constraints decide eligibility, every stage reports its
contribution.

### Entry points and construction

```python
from app.recsys import build_system, get_catalog
from app.recsys.pipeline import Pipeline, PipelineConfig
from app.recsys.dense import DocEmbeddings
from app.recsys.ltr import load_model

pipe = build_system("recsys_serve", get_catalog(), llm=client)       # what the API serves (section 12)
# or explicitly, with injected resources:
pipe = Pipeline(catalog, PipelineConfig(...), name="custom",
                doc_embeddings=DocEmbeddings.load(), ltr_model=load_model("v1_noapi"), llm=client)

rec = pipe.recommend(query, k=10)          # sync: scripts, offline evaluation (uses asyncio.run)
rec = await pipe.arecommend(query, k=10)   # async: FastAPI handlers (never call recommend() inside a loop)
explanation = explain(rec)                 # app.recsys.explain -> pydantic model, .model_dump(by_alias=True)
```

- `app/recsys` never imports `evalkit`. Resources: the catalogue (`get_catalog()`), the committed
  document matrix `app/recsys/artifacts/doc_embeddings.npz`, the committed models
  `app/recsys/artifacts/ltr_v1.json`, `ltr_v1_noapi.json`, `ltr_v1_noapi_nocap.json` (served) and
  `ltr_v1_noapi_nosusp.json`, and an `app.llm` client (default
  `get_client()`). Everything loads once per process (catalogue memo, model cache); a `Pipeline` holds no
  per-request state, so one instance serves concurrent requests.
- The learned ranker is evaluated in numpy (`TreeEnsemble`); LightGBM and OpenMP are needed only for
  training. On load the model re-predicts a stored reference batch and refuses to serve if it disagrees
  with LightGBM's own predictions.
- With `LLM_PROVIDER=mock` (tests, CI) the pipeline runs end to end: query embeddings, ranking and the
  document matrix (built in memory from the catalogue) all come from the mock provider. If the real
  embedding provider differs from the one that produced the committed matrix, construction of the dense
  stage fails loudly instead of comparing vectors from different models.

## 2. Hard filters (3a)

Same predicates as the evaluation's violation metric and rule-graded judgements
(`HardConstraints`): route category in the tab, great-circle distance home → start within the travel
radius, length within the absolute distance cap. Before/after: RESULTS.md "Phase 3 ablation",
Violations@10 of `v0_rules` vs `v1_filters`.

- **Missing slot** → that constraint is not applied, and the verdict says `"applied": false` with
  `null` distances; it never claims a check that did not happen. No tab → all categories. Unknown tab →
  empty set (the caller should validate the tab).
- **Tiny eligible set** (fewer than 10 routes) → only the radius widens, ×1.25 per step, at most 2× the
  user's radius. Tab and cap are never relaxed: the tab is what the user asked for, the cap is their
  absolute limit. Routes admitted by a widened radius are marked `relaxed` with both the user's limit
  and the limit used, so a UI can say "nothing closer than this". If even the widest
  radius leaves fewer than k routes, the list is short: padding with infeasible routes would hide the
  problem.
- Without an intent the request is still served (section 6).

## 3. Candidate generation (3b)

All measurements: RESULTS.md "Candidate generation" (test Recall@50 and standalone NDCG@10 per
generator; dev tuning tables).

**BM25F** (`bm25.py`): per-field BM25 with field weights, IDF over the whole catalogue (stable across
requests), numpy postings, matched terms with their contribution per route for the explanation.
Text questions, decided on dev rather than assumed (`make cg-tune`):

- *German titles vs English intents*: a German→English glossary with crude decompounding
  (`Staffelseerundweg` → lake, loop) seemed the obvious fix. Measured, it **lowers** recall: Bavarian
  place names are full of the same morphemes (-berg, -bach, -see, -tal, Kirch-), so "summit" and "lake"
  fire on every Nürnberg and Kirchberg. It is implemented, tested and **off**. The English generated
  descriptions already carry the facts the titles hint at.
- *Light stemming* (both sides) and *negation scopes* ("no busy roads" removes "busy roads" from the
  query) and a *small query-side synonym list* towards the catalogue vocabulary (loop → circular,
  pub → refreshment, stroller → pushchair) help.
- *Field weights*: tags ×2 (the controlled vocabulary), title ×0.5 (mostly names); description-only
  BM25 loses less than title+tags-only.
- Bias in this tuning: the pool contains plain BM25 of the intent, so the plain variant's routes are the
  best judged ones; the comparison leans towards plain, not away from it.

**Dense** (`dense.py`): `gemini-embedding-001` on Vertex, 768 dimensions (Matryoshka truncation,
renormalised), `RETRIEVAL_DOCUMENT` for routes and `RETRIEVAL_QUERY` for the intent. Two document texts
were compared on dev: `title_desc` (title + full description) and `facts` (a compact structured card:
shape, activity, length, ascent, difficulty, start locality, tags, named lakes/peaks/sights/huts). The
card wins on dev recall and condensed NDCG, so the committed matrix uses `facts`. Likely reason: the
generated descriptions are long, formulaic and similar to each other, which compresses embeddings into
a narrow band; the card puts the distinguishing facts first.

**Exact search, and when ANN would be needed.** The eligible set is at most a few thousand rows, and
exact cosine is one matrix-vector product. RESULTS.md "Candidate generation" gives the measured time per
query over the *whole* catalogue (no filter) and the catalogue sizes at which exact search alone would
take 10 ms and 50 ms at that rate. Rule for this project: switch to an ANN index (HNSW/IVF, with the hard
filter applied as a pre-filter or by over-fetching) when the full-catalogue scan approaches about a tenth
of the no-API latency budget (50 ms of 500 ms), i.e. around the 50 ms size there, or earlier if many
requests run in parallel on one core. Because the hard filter shrinks the set to the user's region
before scoring, a region-partitioned exact search would scale further than the raw number suggests.

**Committed matrix** in reduced precision: float16 (size in RESULTS.md). int8 with a per-row scale was
measured too: a quarter of float32 but it reorders many near-ties, because cosines sit in a narrow band.
float16 keeps almost all top-10 orders identical; RESULTS.md has both comparisons. The evaluation and
the frozen replay use the committed matrix, so they are consistent with what the API serves.

**RRF** (`fusion.py`), k = 30 (dev: 10-100 within noise). RRF uses ranks only, so BM25 scores
(unbounded, query-dependent) and cosines (narrow band) need no calibration or weight; a weighted score
sum would need both and a tuned weight per query length.

## 4. Ranking (3c)

### (i) Ranker API

The Vertex Ranking API is not enabled in the project (D2), so ranking goes through the client's rank
capability on OpenRouter. A dev pilot (RESULTS.md "Ranker API pilot") re-ranked identical candidate lists
with eight rerankers; quality = condensed NDCG@10 over the judged candidates (same judged subset for all
models, so the comparison is fair without new judgements). **Chosen: `mongodb/rerank-3`** (provider
reports `rerank-3`): best on dev, cheaper and faster than `cohere/rerank-v3.5`. The document text is the
facts card plus the generated description (beats title + description on the same pilot). Query = the
intent as typed. The pilot's labels are pinned (`eval/qrels/rank_pilot_labels.jsonl`, the qrels at
decision time). Caveat: re-scored against the later, deeper dev qrels (with the learned ranker's training
sample) the top few rerankers change order; their differences are within the pilot's noise (40 personas),
so the choice rests as much on cost and latency as on quality.

### (ii) Learned ranker (LambdaMART)

`make ltr-sample` then `make ltr` (`evalkit/ltr.py`); all numbers in RESULTS.md "Learned ranker".

**Training data, dev only.** Rows = the `v4_rrf` fused top 50 of each dev persona (what the ranker sees
at serving time), label = judged grade 0-3. The pooled qrels are shallow and biased towards routes that
some system already put in a top 10, so a seeded uniform random sample of 8 *unjudged* candidates per dev
persona was judged as well (marked `"sample": "ltr-train/v1"` in the qrels). Unjudged candidates are
left out, never treated as negatives. The label set is pinned in `eval/qrels/ltr_train_v1.jsonl`:
evaluating the learned ranker adds judged pairs to the qrels, and reading those would make the training
data depend on the model.

**Features** (`features.py`, 38; no latent field, only the query and the catalogue):

| Group | Features |
|---|---|
| rule sub-scores (v0, questionnaire vector) | `rule_difficulty`, `rule_distance`, `rule_tags` |
| retrieval stages | `bm25`, `bm25_rank`, `dense`, `dense_rank`, `rrf`, `fused_rank` |
| ranker API | `rank_api` |
| geography vs slots | `home_km`, `home_ratio` (distance / radius) |
| length vs slots and intent | `length_km`, `length_cap_ratio` (length / cap), `length_band_pos` (in the questionnaire band), `intent_km_gap` (vs a km figure parsed from the intent) |
| effort | `ascent_m`, `ascent_per_km`, `ascent_fit` (ascent / 75th percentile of routes of this activity in the user's difficulty range), `intent_easy`, `difficulty`, `difficulty_in_range`, `technical`, `duration_h` |
| shape | `is_loop`, `intent_loop`, `loop_match` |
| concepts | `tag_cover`, `tag_hits` (requested concepts present as tags), `neg_hits` (negated concepts present) |
| style | `is_mtb`, `intent_mtb` |
| surface, traffic, popularity, data | `paved_share`, `busy_road_share`, `popularity`, `pois_per_km`, `waymarked`, `osm_description` |

**Training.** LightGBM `lambdarank`, gain 2^g − 1, small trees (15 leaves, ≥ 20 rows per leaf),
learning rate 0.05, bagging and feature fraction 0.8, deterministic single thread. 5-fold
cross-validation **grouped by persona** on dev chooses the number of rounds (best mean fold NDCG@10).
The final model is trained on all dev rows with that number. Test personas are used only to *report*
the frozen models.

**Feature importance**: gain share, split counts and mean |Saabas contribution|, per committed model
(RESULTS.md).

**Where it overfits to the simulated users.** Read the variant table in RESULTS.md with these points:

1. *In-sample vs grouped CV.* Train NDCG on dev rows is far above grouped CV: with few rows per persona,
   the trees memorise personas. Grouped CV is the honest dev estimate; the system-level dev NDCG of
   `v6_*` is in-sample (its training labels) and is never used for a decision.
2. *The largest single gain is `length_cap_ratio`.* That is a property of the simulator: personas'
   absolute caps are generated as the top of their comfortable band times a random factor, and the judge
   reads the band. The ranker learns "about two thirds of the cap is right", which is a fact about the
   generator, not about people. Real users state caps differently (or not at all). Removing the slot
   ratios costs the most of any single group; removing them together with home distance and the intent's
   km figure ("no suspicious") costs more. A deployed model should be retrained on real feedback before
   trusting these features; the "no suspicious" variant is the conservative fallback. System-level rows of both
   (`recsys_v1_nocap`, `recsys_v1_nosusp`, test and dev, 100% judged): section 11 and D19.
3. *Home distance* matters little once the filter has run (the judge does see it), and the *intent km
   figure* adds nothing beyond the slot ratios (intents are written from the same band).
4. *Test above CV* is not a sign of no overfitting: test rows are shallower (only pooled pairs, no random
   sample), so they are easier to order. Compare variants within a column, not across columns.
5. The ranker beats the latent-profile reference matcher on test (RESULTS.md "Reference"): it is trained
   on the judge's grades, so it learns the judge's reading of the catalogue, which a hand-written latent
   utility does not. That is circularity (EVAL.md section 5, point 3), not super-human ranking.

**With vs without the ranker-API feature, and the call.** Grouped CV on dev gives the API feature a small
gain in every fold (RESULTS.md "Learned ranker", per-fold line). The API adds one external call per
request (cost per request and latency: RESULTS.md "Latency and cost against the budget"), and a dependency whose failure would
have to be handled. Decision (D14): **the default system does not call the ranker API.** The dev gain is
small (well under the gain of any earlier stage), while the API adds its per-request cost and multiplies
the median latency (both in the "Latency and cost against the budget" table). If the API's latency or price drops, or real
feedback shows a larger gain, `v7_mmr` is one config change away. Disclosure: the test comparison
(`v6_ltr` − `v6_ltr_noapi`, RESULTS.md "Other comparisons") had been computed before this call was
written down; it agrees in sign with dev and did not change the rule used (dev CV gain vs cost).

## 5. Diversity (3d)

MMR (`mmr.py`) re-ranks the final 50 with relevance = ranker score min-max normalised over the list and
similarity = document-embedding cosine, **also min-max normalised over the list's pairs**. Without that
normalisation lambda barely acts: candidate routes' embeddings are all alike, so the penalty is almost
the same constant for every route (this was found on dev and changed before any test run of MMR).
Diversity is *measured* by ILD@10 on catalogue tag sets, not on embeddings, so MMR does not optimise the
metric directly.

Sweep on dev, every top 10 judged: RESULTS.md "Diversity: MMR sweep" and [mmr_tradeoff.png](mmr_tradeoff.png).
Rule (stated after reading the dev sweep, which is what dev is for): the smallest lambda whose mean dev NDCG@10 loss against lambda = 1 stays below 0.005. **Default lambda = 0.8.**
Honest reading: the diversity gain at any acceptable NDCG cost is small; tags of nearby routes are
similar anyway (same region, same features). MMR is kept because it is cheap, it does no measurable
harm on test at 0.8 (ablation table), and it is the hook for a better similarity (geographic spread,
route overlap) later.

## 6. No intent (questionnaire-only users)

BM25, dense, fusion, the ranker API and the learned ranker all need a text query, and the learned ranker
never saw intent-free rows in training. So without an intent: filter → rule scorer (`v0`) over the
eligible set → MMR. The trace's filter stage says `"fallback": "no_intent"`. This is the best defined
behaviour now; Phase 4's end-to-end comparison measures
it (`recsys_v1_qonly`, RESULTS.md "Phase 4 end-to-end"), and a model trained with intent-free rows could replace it.

## 7. Phase 3 default `recsys_v1`

filters → BM25F + dense (top 100 each) → RRF (k 30, top 50) → learned ranker `v1_noapi` → MMR 0.8. This was
the default at the end of Phase 3 and is the reference row of most comparisons; the API serves `recsys_serve`
(section 12), which differs in the ranker model and adds the feedback and exploration stages.
Its test row, the comparison with `v7_mmr` (same with the API feature) and the latency/cost table
against the budget are in RESULTS.md ("Phase 3 ablation", "Other comparisons", "Latency and cost against the
budget").

**Latency and cost.** Budget: p95 ≤ 500 ms without the ranker API, ≤ 1.5 s with it (query embedding
included). `make latency` measures warm, sequential, cache-off requests end to end; both `recsys_v1`
and `v7_mmr` are compared with their budget there. The dominant stage is the upstream call: the query
embedding for `recsys_v1`, the ranker API for `v7_mmr`; local compute (filter, BM25, features, trees,
MMR) is a small fraction. The query embedding has a long tail (the max in that table); a production
deployment should put a timeout on it and fall back to BM25-only candidates when it fires. Cost per
request is the embedding of one short intent for `recsys_v1`, plus one rerank call for `v7_mmr`.
The evaluation's own latency column (RESULTS.md "Latency") is higher at p95 because it replays the
latency recorded for the first, cold calls of each batch run.

## 8. Explanations

Every stage writes its per-route contribution into its `StageTrace.contrib`; `app.recsys.explain`
validates them into `RecommendationExplanation` (pydantic; `explanation_json_schema()` returns the JSON
schema; version `recsys.explanation/v1.1`). A stage that did not run is `null`, never filled with
defaults. v1.1 (iteration 2) only adds the optional stage `needs`; every v1 field is unchanged, so a reader of
v1 that ignores unknown stages reads v1.1 unchanged (the API and the UI accept both).

```
RecommendationExplanation
  schema_version  "recsys.explanation/v1.1"
  request_id, system
  routes[]        RouteExplanation
    route_id, rank, score (final score: MMR score, else ranker score)
    stages
      filter      verdict pass | pass_relaxed | fail
                  category {applied, ok, value, allowed[]}
                  radius {applied, ok, distance_km, limit_km, limit_used_km, relaxed}
                  distance_cap {applied, ok, length_km, limit_km}
      v0_rules    difficulty, distance, tags (weighted sub-scores), total, feedback_penalty?
      bm25        score, rank (among eligible), matched_terms[{term, contribution}]
      dense       similarity (cosine), rank
      fusion      rrf_score, rank, k, inputs {bm25: rank, dense: rank}
      rank_api    score, rank, model
      ltr         score, rank, bias, model,
                  features[{name, value|null, contribution}]   all features, largest |contribution| first;
                                                               score = bias + sum(contributions) (Saabas)
      mmr         lambda, relevance, max_similarity, penalty, mmr_score, rank_before, rank_after
      feedback    relevance, embedding_affinity, tag_affinity, near_duplicate_of, duplicate_penalty,
                  score, rank_before, rank_after                       (Phase 5; only with feedback events)
      explore     cluster, label, theta, posterior [a, b], source, position,
                  reason "shown to learn your taste"                   (Phase 5; the explored route only)
      needs       mode, met, unmet, rank_before?, rank_after?, demotion?   (v1.1; only when a need was stated)
                  checks[{need, label, phrase, source, applied, applied_level, met_level, ok, strict,
                          fact ("no steps, 94% of the route on stroller-suitable surface, 120 m of climbing"),
                          threshold, values{raw catalogue numbers}}]
  stages[]        StageSummary {stage, n_in, n_out, local_ms, upstream_latency_ms, upstream_cost_usd, info}
```

A real example (the Phase 3 default `recsys_v1`, one test persona, top route, all stages) is generated by
`python -m evalkit.explain_example` and rendered in RESULTS.md "Explanation example". Tests:
`tests/recsys/test_pipeline.py` runs every registered pipeline on the mock provider and validates the
schema, the stage set per system, LTR contributions summing to the score, and MMR ranks.

For a UI: show the filter verdict as facts ("23 km from home, limit 30"), BM25's matched terms as "matches
your words", the top 3 LTR contributions by absolute value with their feature values, and the MMR
rank change when it is non-zero. Wiring this into the API and the score modal is the API/UI owner's job.

## 10. Feedback and exploration (Phase 5)

Code: `feedback.py`, `explore.py`, wired into `pipeline.py`; tests `tests/recsys/test_feedback.py`,
`test_explore.py`. Simulation protocol and behaviour model: EVAL.md section 10. Results: RESULTS.md "Feedback
loop" and [convergence.png](convergence.png). Decisions D20-D22.

**Signals.** `UserQuery.feedback` carries `FeedbackEvent(route_id, reason, age_days)`: the four negative
reasons of the product (`too-hard`, `too-easy`, `too-far`, `not-interested`) and `completed` (a souvenir
record). Every event gets one weight, `calculate_time_decay_weight(age, 60)` = `0.5 ** (age / 60)`: the
baseline's decay function with the Phase 0 fix (a true half-life), called with **60 days for both signs** (D20;
the baseline's own default stays 30 days). `too-far` means *too far to
travel* (the UI shows a car), not "too long": v0 reads it as route length, the new pipeline as distance from
home.

**Applied once, from the original query.** `adjust_query` takes the profile as stored and all events and
returns a new query whose `feedback` is empty; nothing adjusted is ever written back, so feedback cannot
compound (D7 point 1). It changes:

| What | Rule (per event, decayed weight w) | Clamp |
|---|---|---|
| difficulty range | `too-hard` −s·w, `too-easy` +s·w, one net shift | 0..3, width ≥ 1 |
| distance cap (hard filter) | `too-hard` on a route ≥ 0.6 × cap pulls the cap s·w of the way to 0.9 × its length (shorter routes: effort, not length, so no change) | ≥ ½ the user's cap |
| travel radius (hard filter) | `too-far` pulls the radius s·w of the way to 0.9 × the route's distance from home | ≥ ½ the user's radius |
| minimum distance (vector) | `too-easy` on a short route raises it towards 1.1 × its length | ≤ 0.8 × maximum |
| tags | net preference per content tag `(pos − neg) / (pos + neg + 1)`; positive tags join `preferred_tags`, negative ones leave it and go to `avoided_tags` | – |
| route effects | completed or rejected routes with w ≥ 0.25 (two half-lives) are not shown again; older ones may return | – |

**Rocchio.** `q' = alpha q + beta c_pos − gamma c_neg` (unit length) with decay-weighted centroids of the
document embeddings of completed (`c_pos`) and `not-interested` (`c_neg`) routes; effort and distance reasons
do not move the embedding. `q'` replaces the intent embedding in dense retrieval (so the fused candidates and
the ranker's dense features move). **No intent** (questionnaire only): there is no `q`; the pipeline stays on
its rule-scorer path and the feedback direction `beta c_pos − gamma c_neg` is used only in re-scoring.

**Feedback stage** (after the ranker, before MMR): relevance = ranker score min-max normalised over the
candidates, `+ eta_emb ×` cosine to the feedback direction (centred, scaled over the candidates)
`+ eta_tag ×` tag affinity `− nu_dup × w` for near-duplicates (same activity, start within 1 km, length within
25%) of a rejected or completed route; excluded routes are removed. Every route's terms are in the trace.

**Parameters** (`FeedbackConfig`, chosen on dev, D21): half-life 60 days, route-effect window w ≥ 0.25, slot
steps 0.25, and **Rocchio and re-scoring off** (beta = gamma = eta = nu = 0): on the dev grid no setting with
them beat route effects + slot steps, and larger weights lost. `recsys_v1_fb` uses these; `recsys_v1_fb_light`
(beta 0.25, gamma 0.1, eta_emb 0.1, eta_tag 0.1, nu_dup 0.15, same slot steps) keeps the full loop runnable and
is reported next to it; on the test simulation it does better than the dev choice (RESULTS.md), which is the
kind of dev/test disagreement D21 discusses.

**Exploration** (`ExploreConfig`, `recsys_v1_fb_explore`). Clusters from catalogue content only: content
tags of every route as IDF-weighted unit vectors, seeded spherical k-means (k = 8, best of 5) plus a
"no theme tags" cluster; labels are each centroid's three heaviest tags. Per user and request, cluster c has
Beta(1 + S_c, 1 + F_c) with S_c / F_c the decayed weight of completed / `not-interested` routes in c (effort
and distance reasons do not count against a theme). While the user has fewer than 10 events (cold start),
rank 10 is reserved: one Thompson draw per cluster from a generator seeded by (seed, request id, number of
events); among clusters with an eligible route and not already in ranks 1-9 (all if every one is), the
largest draw wins; the route is that cluster's best candidate below rank 9 in the pipeline's order, else its
eligible route most similar to the query (seeded random without one). It comes from the filtered eligible
set (so it passes every hard filter) and is never an excluded route. Trace: stage `explore` with the
cluster, draw, posterior and `"shown to learn your taste"`.

**Functions the API calls.** Build events from stored rows with
`app.recsys.feedback.feedback_events_from_rows(feedback_rows, souvenir_rows, now=None)` (rows: objects or
mappings with `route_id`, `reason`, `created_at`; souvenirs `route_id`, `completed_at`; naive timestamps are
UTC), put them on the **original** profile's query (`dataclasses.replace(query, feedback=events)`), and serve
`build_system("recsys_serve", catalog, ...)` (section 12). Never store the adjusted vector.

## 12. The served system: `recsys_serve`

`build_system("recsys_serve", ...)` (`SERVED_SYSTEM` in `systems/pipelines.py`) is what the API serves
(D25): filters → BM25F + dense → RRF → learned ranker `v1_noapi_nocap` (no
`length_cap_ratio`, D19) → feedback stage (route effects + slot steps, dev-chosen, D21) → MMR 0.8 → exploration
slot at rank 10 while the user has fewer than 10 feedback events (D22). Rocchio and re-scoring are off in the
dev-chosen feedback settings, so feedback changes the request's slots and tags and hides routes but does not move the
query embedding. Its twin without exploration is
`recsys_serve_noexplore`. `recsys_v1` remains the Phase 3 default of the ablation and is not what is served.
Numbers: RESULTS.md "Served default" (single request and simulation).

**Empty slots** (`systems/empty_slots.py`, RESULTS.md "Empty profile slots"): without a distance cap no length
filter applies and the ranker has no cap to compare with, so longer routes than the user can do reach the list;
the served ranker degrades less there than `recsys_v1`'s. Without a home there is no radius filter at all and
most of the list is out of reach; nothing downstream substitutes, so the product must collect the home (the
chat treats the place as required).

## 13. Iteration 2: stated needs (`needs.py`)

The design principle says verifiable constraints decide eligibility; until iteration 2 only the three profile
slots were verified. The failure analysis (FAILURES.md, test) showed the learned ranker outweighing needs the user
had *stated* and the catalogue can *check*. This stage turns those into constraints. Where the hypothesis came
from and how it was evaluated: EVAL.md section 12; the decision: DECISIONS.md D27; numbers: RESULTS.md "Iteration
2". **It is built, tested and registered, and off in the served default** (D27).

**Extraction** (`extract_needs(intent, category, slot_needs)`): regular expressions over the intent, English and
German, after lower-casing and normalising quotes and dashes. A mention is negated if a negator ("no", "not",
"without", "instead of", "don't", "kein", "ohne", "nicht", ...) comes at most five words before it in the same
clause with no scope-breaking word ("with", "reachable", "mit", ...) in between, or if "not needed / optional /
egal" follows it; negated mentions are reported as `ignored`. Structured needs from the chat or the profile arrive as
`UserQuery.needs` codes (`"stroller"`, `"train"`, `"mtb"`, `"loop"`, `"one_way"`, `"days:3"`, `"duration_h:2"`,
`"max_km:12"`) and win over the text. No model call; extraction takes well under a millisecond.

| Need | Triggers (examples) | Verified by | Levels, strict → loosest | Why this threshold |
|---|---|---|---|---|
| `stroller` | stroller, pram, pushchair, buggy, Kinderwagen | `profile.steps_m` (O), `profile.stroller_ok_share` (O), max(ascent, descent) (D) | no steps, ≥ 50% stroller-suitable surface, ≤ 200 m; no steps, ≤ 300 m; no steps | steps cannot be pushed; 200 m is the catalogue's own stroller-tag rule; the surface share is "most of the way" |
| `no_steps` | no steps / stairs, step-free, wheelchair, barrierefrei, keine Treppen | `profile.steps_m` (O) | no steps | literal |
| `train` | by train, railway, station, S-Bahn, mit dem Zug, Bahnhof | `Train access` (station ≤ 1 km of the start), `near_end.train_station` (O) | station at the start; at the start or at the end of a one-way route; any public transport at the start | the catalogue's train-access radius; a one-way route is walked from the end too |
| `public_transport` | public transport, by bus, no car, car-free, ÖPNV | `Public transport access` (O) | train 1 km / tram 500 m / bus 300 m at the start | the catalogue's tag |
| `mtb` (cycling tab only) | mountain bike, MTB, singletrail, enduro | `activity` (O), `profile.paved_share` | an MTB relation; MTB relation or ≤ 50% paved | MTB relations are few (2% of the catalogue); a mostly unpaved ride is the nearest substitute |
| `loop` / `one_way` | loop, circular, round trip, Rundweg / one-way, linear, A to B, Streckenwanderung, "not a loop" | `is_loop` (D: start and end within 300 m) | the shape | both stated → neither |
| `days` | four-day, 3 days, multi-day, weekend, a week, mehrtägig, dreitägig | `length_m` (D) | ≥ N × a short day (5 km on foot, 20 km by bike, 15 km MTB); × 0.75 | a deliberately low floor: N days must be longer than N short days; "multi-day" without a number = 2 |
| `length` | around 8 km (→ 4-12), 5-10 km (→ 4-12), at least 20 km, short (chat band: ≤ 8 km on foot), long (≥ 10 km) | `length_m` (D) | the window; widened by a third | "around X" is generous on purpose; distances followed by "of / from / away" are how far the start is, not a length |
| `max_length` | no more than / at most / up to / within / höchstens X km | `length_m` (D) | X (+10% with "about"); +25% | an upper bound is a bound, not a target (FAILURES.md P260) |
| `duration` | 2 hours, half-day, full day | `duration_min` (D, DIN 33466 / planning speeds) | 0.5-1.5 × the hours; widened by a third | moving time without breaks, so the window leans short |

O = observed in OSM, D = derived by the pipeline (DATA.md section 6). Extractor precision and recall per need on dev
intents, against the personas' latent profiles where one corresponds: RESULTS.md "Iteration 2".

**Three ways to use them** (`NeedsConfig.mode`), compared on dev:

- `filter` (`recsys_serve_needs`): after the hard filter and before candidate generation, the eligible set keeps
  only routes that meet every need at its current level. Retrieval, ranker, MMR and exploration then work inside
  that set, so the exploration pick meets the needs too.
- `filter_promote` (`recsys_serve_needs_promote`): the filter, and when it had to relax, the routes that meet every
  need strictly (fewer than the floor, by construction) are added to the candidates if retrieval missed them and,
  after MMR, the list is stably re-ordered by the demotion key below. This is the variant that fixes "four-day
  tour" queries whose few qualifying routes the plain filter gives up.
- `demote` (`recsys_serve_needs_demote`): nothing is removed; after MMR the candidate list is stably re-ordered by
  the demotion key, the sum over needs of (strictest level met / number of levels), 1 for a need not met at any
  level.

**Relaxation and floor.** The floor is 20 routes (twice the list length): fewer than that leaves the ranker, MMR
and the exploration slot nothing to choose from. Below the floor, needs are relaxed one at a time in this order,
each through its levels and then dropped: `length`, `duration`, `loop`, `one_way`, `days`, `mtb`,
`public_transport`, `train`, `max_length`, `no_steps`, `stroller`. Preferences about the shape of the outing go
first, needs that decide whether the party can do the route at all go last. A need is never relaxed while the
floor is met, and an eligible set already smaller than the floor is not cut further. The trace (`needs` stage
info) lists `applied`, `relaxed` (with the level), `dropped`, every relaxation step with the counts before and
after and the reason ("only 3 routes met every need (floor 20)"), the strict count and, for promotion, how many
routes were added to the candidates. The radius is not widened for a need (the hard filter's own tiny-set rule,
section 2, still applies first).

**Explanation and serving.** Every returned route gets one check per stated need with the catalogue's numbers
(`fact`), the rule (`threshold`), the raw values, whether it was enforced and at which level. The API returns them
in the per-route explanation (schema v1.1); the one-line reason names up to two met needs ("you asked for
stroller-friendly: no steps, 94% of the route on stroller-suitable surface, 120 m of climbing") and the first unmet
one; the score modal shows a "What you asked for" line (SERVING.md "Explanations"). The chat's structured slots
reach the stage through `UserQuery.needs` (activity `mtb`, the tags `Suitable for strollers`, `Train access`,
`Public transport access`, `Round trip`, `Linear route`, `Multi-stage route`, and a stated duration).

**Cost.** Extraction and the per-need masks are numpy over arrays built once per catalogue; the stage's own compute
is well under a millisecond at p95 on dev (RESULTS.md). No upstream call.

**What it showed.** By the rule fixed in advance on dev, no variant is accepted (D27). The dev comparison is
dominated by the learned ranker being in-sample on dev; with a cross-fitted ranker every variant is ahead on dev,
and test agrees (reported once). Where it hurts, the catalogue's check is stricter than the judge's reading
(FAILURES.md "Iteration 2"). Next step, if the owner wants it: pre-register a cross-fitted dev rule, loosen the
train check to "station at either end or public transport" only if dev says so, and keep promotion from
resurrecting needs the relaxation dropped.
